# Epicor PR Automation - Project Specification

## 1. Project Overview
The **Epicor PR Automation Tool** is a specialized web application designed to streamline the creation of Purchase Requisitions (PR) in the Epicor ERP system. By automating the repetitive task of manual data entry from Excel spreadsheets into the Epicor web interface, it reduces human error and significantly increases productivity for procurement teams.

## 2. Target Users
- Procurement Officers
- Supply Chain Managers
- Project Coordinators
- Anyone responsible for creating frequent PRs in Epicor based on structured part lists.

## 3. Key Features
- **Web-Based Interface**: Modern, responsive UI with a step-by-step workflow (Credentials -> File Selection -> Execution).
- **Excel Data Processing**: Intelligently parses specific columns from standardized Excel part lists.
- **Filtered Execution**: Allows users to select specific line items (by their "No" column) to process, rather than the entire file.
- **Intelligent Browser Automation**: Uses Playwright to navigate the Epicor web portal, handle logins, and iteratively build PR lines.
- **Real-Time Monitoring**: A live "Activity Log" provides immediate feedback on every step of the automation process via Server-Sent Events (SSE).
- **Generated PR Capture**: Automatically extracts and displays the new PR number generated by Epicor upon successful completion.

## 4. Technical Architecture

### 4.1 Backend (Node.js & Express)
- **Framework**: Express.js handles API routing and static file serving.
- **Automation**: Playwright (with Chromium) manages the browser interaction layer.
- **File Management**: Multer handles temporary Excel file uploads.
- **Data Parsing**: `xlsx` library extracts data from complex spreadsheet structures.
- **Messaging**: Server-Sent Events (SSE) provide a one-way communication channel from the server to the client for real-time logs.

### 4.2 Frontend (Vanilla Web Tech)
- **Structure**: Semantic HTML5.
- **Logic**: Vanilla JavaScript for DOM manipulation, file drag-and-drop, and SSE handling.
- **Styling**: Modern CSS with Glassmorphism effects, CSS Grid layouts, and interactive animations.

## 5. Automation Workflow

1.  **Authentication**: The server launches a Chromium instance and navigates to the Epicor Requisition Entry page.
2.  **Header Generation**:
    *   Logs in with provided credentials.
    *   Clicks "New Requisition" and saves to trigger the generation of a new PR Number.
    *   Extracts the PR Number to display back to the user.
3.  **Line Iteration**:
    *   For each "No" value specified by the user, the system locates the corresponding row in the Excel data.
    *   It creates a "New Line" in Epicor.
    *   It navigates to the "Line Detail" view.
    *   It populates: Part Code, Class, Description, Supplier, Quantities (Default: 1), and Unit Price.
    *   It saves the line and proceeds to the next until all requested items are added.
4.  **Completion**: Closes the browser and reports success.

## 6. Data Requirements (Excel Schema)

The tool expects an Excel file with a specific structure to function correctly.

| Field | Requirement |
| :--- | :--- |
| **Sheet Name** | Must be named `PART CODE - TABLE FORM` |
| **Header Row** | Data headers must be on **Row 3** of the sheet. |
| **Data Rows** | Start from Row 4 onwards. |

### Required Columns
The following columns (checked by header name) must exist:

1.  **No**: A unique numerical identifier for the row (used for filtering).
2.  **Requisition Part Code**: The numeric or alphanumeric part code in Epicor.
3.  **Description**: Used to populate the **Class** field in Epicor.
4.  **Description.1**: Used to populate the **Description** field in Epicor.
5.  **Supplier Code**: The vendor code in Epicor.
6.  **Price**: The unit price for the item.

## 7. Security & Best Practices
- **Credential Handling**: Passwords are transmitted to the server via POST body and are only used within the transient Playwright session. They are not stored in any database.
- **File Cleanup**: Uploaded Excel files are processed in-memory (via temporary disk storage) and are deleted immediately after the automation run finishes or fails.
- **Headless Toggle**: Currently configured to run in *non-headless* mode (visible browser) to allow users to monitor progress and handle any unexpected Epicor prompts if necessary.
